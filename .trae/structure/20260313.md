# java_swarm 三模块结构分析与优化方案（2026-03-13）

## 1. 范围与结论摘要

本次分析仅覆盖 `common`、`main-service`、`subagent-service` 三个 Maven 模块，结合当前工作区代码与 Git 状态进行静态研判。  
总体结论：

- 架构分层清晰：`common` 负责 DTO/LLM 能力，`main-service` 负责编排与流式输出，`subagent-service` 负责子 Agent 注册与应答。
- 主链路已具备“并行子 Agent + 汇总判官 + 心跳保活”的完整 SSE 能力，核心在 `OrchestratorService`。
- 目前存在较明显的工程化风险点：数据目录定位不一致、运行期路径依赖强、异常降级策略混杂、并发与背压策略可进一步收敛。
- 可按“稳定性优先”路径进行优化：先统一路径/配置与错误语义，再做并发限流与可观测性增强。

## 5. 代码逻辑总结（Code Logic Summary）

### 5.1 common

- 定义跨服务 DTO：请求、子 Agent 信息、子 Agent 回复等。
- 定义 LLM 抽象：`LlmClient` 与工厂 `LlmClientFactory`。
- `RealQwenLlmClient` 同时支持同步调用与流式调用（SSE chunk 解析、401/429重试、并发令牌池）。
- `QwenKeyPool` 提供多 Key 轮询与并发控制能力。

### 5.2 main-service

- 对外接口：`POST /api/shopping/stream`，返回 `text/event-stream`。
- `OrchestratorService` 是核心编排层：
  - 先生成公共问题（question 流）；
  - 并行拉取子 Agent 列表并发起问答；
  - 收集有效子 Agent 回复后触发 summary 流；
  - 注入 heartbeat，直到 summary 出现后停止。
- `SubAgentDirectoryService` 与 `SubAgentDialogueService` 通过 WebClient 访问 `subagent-service`。
- `LlmStreamService` 对 summary 事件有“流式为空时退化为同步生成”策略。

### 5.3 subagent-service

- `SubAgentRepository` 从 `data/subagents.json` 加载子 Agent 定义，并按类型过滤启用项。
- `SubAgentController` 暴露：
  - `GET /api/subagents`：返回子 Agent 列表；
  - `POST /api/subagents/{id}/reply`：拼接 prompt + GoodsInfo + question/context，调用 LLM，输出带报价的回复。
- 报价策略是当前的简化模拟：预算减去与 `agentId` 哈希相关的 delta，并设最小值 100。

## 6. 典型调用流（Typical Call Flow）

1. 客户端调用 `main-service`：`POST /api/shopping/stream`。
2. `StreamingShoppingController` 转发给 `OrchestratorService.stream`。
3. `OrchestratorService` 调用 `LlmStreamService` 产出 `question` 事件。
4. 并行调用 `SubAgentDirectoryService.fetchAgents("shopping")` 拉取子 Agent。
5. 对每个 agent 调用 `SubAgentDialogueService.requestOnce`。
6. `subagent-service` 的 `SubAgentController.reply` 读取 prompt / goodsInfo，调用 `LlmClient` 生成建议并附带 quote。
7. `main-service` 将每个子 Agent 结果封装为 `subAgentReplay` 事件实时回传。
8. 所有子 Agent 完成后，`OrchestratorService` 组装 judge 输入并触发 `summary` 事件。
9. 主流与 heartbeat 合并输出，遇到 `summary` 后停止。

## 7. 关键问题与优化方案

### 7.1 路径与配置一致性（高优先级）

现状问题：

- `PromptService` 直接从 `user.dir/data` 读取，而 `OrchestratorService` 判官 prompt/goodsInfo 使用“向上回溯 + 多候选路径”。
- `QwenKeyPool` 默认 keys 路径为硬编码绝对路径，可移植性差。
- `subagent-service` 的数据目录选择逻辑较完善，但 `main-service` 同类能力不足。

优化建议：

1. 统一引入 `DataPathResolver`（common或各服务内）：
   - 支持显式环境变量优先；
   - 支持模块目录与根目录候选；
   - 对外仅暴露“读 prompt / profile / goodsinfo”的统一入口。
2. 将 Qwen keys 默认路径改为相对项目路径候选 + 环境变量覆盖，不依赖单机绝对路径。
3. 为路径解析增加启动期日志（仅输出存在性和最终选中路径，不输出敏感内容）。

### 7.2 编排层并发与背压（高优先级）

现状问题：

- `OrchestratorService` 对 agent 调用并发固定为 10，未与实际 agent 数量、系统负载、下游限流联动。
- `Flux.merge(heartbeat, mainFlux)` 在异常场景的终止语义较隐式。

优化建议：

1. 并发参数外置化（如 `orchestrator.agent.max-concurrency`）。
2. 为子 Agent 调用增加超时、重试与熔断策略（建议在 `SubAgentDialogueService` 层统一）。
3. 对 summary 触发条件增加可观测指标（有效 replay 数、耗时、空流原因）。

### 7.3 错误语义与事件协议（中高优先级）

现状问题：

- 当前 fallback 场景混合字符串与 JSON，对前端消费不够统一。
- `subAgentReplay` 同时有“真实回复”和“DONE”事件，依赖消费者正确过滤。

优化建议：

1. 统一事件数据协议，固定字段如 `type/id/message/meta/fallback/reason`。
2. DONE 事件改为独立 eventName（如 `subAgentDone`），减少下游歧义。
3. 为 `error`/`fallback` 建立枚举化 reason code（便于监控与告警）。

### 7.4 可测试性与回归防护（中优先级）

现状问题：

- 已有回归测试覆盖关键链路，但更多聚焦编排逻辑，路径解析与配置组合场景覆盖不足。

优化建议：

1. 增加路径解析参数化测试（不同 `user.dir`、环境变量、目录缺失组合）。
2. 增加 `subagent-service` 对 prompt/goodsinfo 缺失场景的契约测试。
3. 增加 SSE 事件顺序与字段完整性测试（question → subAgentInfo → subAgentReplay* → summary）。

### 7.5 可观测性与运维（中优先级）

优化建议：

1. 关键链路增加结构化日志字段：traceId、requestId、agentId、event、latencyMs。
2. 增加基础指标：Qwen 调用成功率、429/401 次数、summary 生成耗时、空 summary 比率。
3. 对外暴露健康检查项：数据目录可读性、Qwen key 可用性、下游 subagent 可达性。

## 8. 分模块落地路线（建议）

### 第1阶段（1~2天）

- 统一路径解析组件，替换 `PromptService` 与 `OrchestratorService` 的散落读取逻辑。
- 外置并发与超时参数。
- 统一 `subAgentReplay` / `summary` / `error` 的数据结构。

### 第2阶段（2~3天）

- 引入重试与超时治理（按服务层封装）。
- 增加路径解析与协议一致性测试。
- 补齐基础指标和日志字段。

### 第3阶段（持续优化）

- 根据线上指标调优并发与心跳策略。
- 抽离“报价策略”为独立策略接口，支持规则化或模型化升级。
