## 目标

* 前端“日志输出/页面流式日志”统一增加时间戳，格式为 `YYYY-MM-DD HH:mm:ss.SSS`（例如 `2026-02-25 14:35:20.123`）。

* 调整后端用户对话编排，使以下阶段尽可能“就绪即发”，且仅 summary 阶段需要等待前置阶段全部完成：

  * 立即查询 subAgent 并输出 `event=subAgentInfo`

  * 输出用户分析过程 `event=question`

  * 循环请求 subAgent，并在每个 subAgent 回复组装完成后立刻输出 `event=subAgentReplay`

  * 在所有 subAgent 回复结束后输出 `event=summary`，最后输出 `event=done`

## 现状梳理（基于当前工作区代码）

* 前端仅有一个静态页面：`main-service/src/main/resources/static/chat_stream.html`，内部包含：

  * 统一追加“页面日志流”的入口：`append(tag, text)`（目前不带日期且不带毫秒）

  * SSE 事件分发：`handleEvent({evt,data})`

* 后端流式编排核心在 `OrchestratorService.stream(...)`：

  * `subAgentInfo` 通过拉取 subAgent 列表后输出（当前实现会等待列表收集完成）

  * `question` 为 LLM token 流

  * `subAgentReplay` 为每个 subAgent 完整回复（当前是一次性返回，不是 token 级）

  * `summary` 为 LLM token 流

## 方案概览

### 1) 前端时间戳（日志输出）

实施点位（最小改动、可控影响）：

* 改造 `fmtTime(ts)`：输出 `YYYY-MM-DD HH:mm:ss.SSS`，并用于：

  * `stats.startAt` 展示

  * 页面“流式响应”日志（events）每行前缀时间

* 改造 `append(tag, text)`：存储结构从 `{tag,text}` 扩展为 `{ts,tag,text}` 或直接把时间拼进 `tag/text`（两种实现二选一，优先结构化 `ts`，UI 更清晰）

* 可选增强（若你希望“控制台日志也带时间”）：封装 `logInfo/logDebug/logError`，在调用 console.\* 时统一追加时间戳前缀，并替换页面内的 console 调用点

验收标准：

* 页面展示每一行日志都带形如 `2026-02-25 14:35:20.123` 的时间戳

* 控制台（可选增强）同样带该格式前缀

### 2) 后端对话流程（就绪即发、summary 阻塞）

关键原则：

* `subAgentInfo` 不应被后续步骤（question / subAgentReplay / summary）阻塞；一旦查到结果就能立刻向客户端发出

* `question` 为“用户分析”阶段，可流式输出 token

* `subAgentReplay` 阶段应逐个 subAgent 并发/串行请求（按你的偏好选择），每个 subAgent 完成后立即 emit 其 SSE 事件

* `summary` 必须等待 `subAgentReplay` 全部结束后开始（该阶段允许阻塞）

具体改造步骤：

1. 将 subAgent 查询拆为可复用的 `agentsFlux`（已能缓存共享），并决定 `subAgentInfo` 输出策略：

   * 策略 A（兼容当前前端）：仍旧输出一次 `subAgentInfo=[...]`（数组），但确保其 Flux 与后续步骤并行（不会等 summary）

   * 策略 B（更“就绪即发”）：支持多次输出 `subAgentInfo`（增量：单个 agent 或小批量），同时前端调整为支持增量 upsert（不再要求必须一次性数组）
2. 保持整体阶段顺序：

   * `subAgentInfo`（可并行于后端准备，但对客户端应尽早到达）

   * `question`（流式）

   * `subAgentReplay`（在 question complete 后开始；每个 agent 完成即发）

   * `summary`（等待 subAgentReplay complete 后开始）

   * `done`
3. 明确 subAgent 请求并发模型（默认建议并发，保持“谁先完成谁先发”）：

   * 并发：`flatMap`（更快，输出顺序按完成先后）

   * 串行：`concatMap`（更可预测，严格按 agent 列表顺序）
4. 保持 `done` 中的统计取值为“订阅时刻计算”（避免过早取值），并确保 `bestQuote/bestAnswer` 的更新发生在 reply 到达时

验收标准：

* 客户端能先收到 `subAgentInfo`，不需要等 summary

* `question` token 持续输出

* 每个 subAgent 的回复在该 subAgent HTTP 返回后立刻出现在页面（不等其他 subAgent）

* `summary` 只在所有 subAgent 结束后输出

* `done.bestQuote` 与实际最低报价一致

## 验证方式

* 本地启动 main-service 后，用 `chat_stream.html` 手动发起一次流式请求，观察：

  * 页面日志时间戳格式正确（含毫秒）

  * `subAgentInfo → question → subAgentReplay(多次) → summary → done` 顺序与“就绪即发”的时机符合预期

* 运行 `main-service` 相关 Maven 测试，确保编译与用例通过
