# 三商家定价与优惠策略 Prompt 重构计划（Plan）

## 1. 目标定义

* 仅针对 3 个测试商家 Prompt 重构角色与定价规则，不改 YAML/YML 配置。

* 让同一商品 A 在三类商家下体现不同“进货价-挂牌价-券后价（最终quote）”逻辑。

* 明确“商家只公开指导价；内部有进货价与挂牌价；最终给用户的是折扣后报价”这一价格分层。

* 保持现有结构化输出协议不变：`product_id, quote, reason_tags, coupon_info, risk_flags, cta`。

## 2. 当前实现与约束基线

* Prompt 文件位置：

  * `subagent-service/data/baonuanneiyi/prompts/seller_a.txt`

  * `subagent-service/data/baonuanneiyi/prompts/seller_b.txt`

  * `subagent-service/data/baonuanneiyi/prompts/seller_c.txt`

* 子代理注册映射位于 `subagent-service/data/subagents.json`，A/B/C 均已启用并绑定上述 prompt。

* `SubAgentController` 会二次兜底修正结构化字段，尤其 `coupon_info` 必须包含：
  `original_price, after_coupon_price, subsidy_by, stackable, coupon_desc`。

* 因此重构 Prompt 时必须强制“字段完整且价格自洽”，避免被后端兜底覆盖。

## 2.1 代码影响评估（基于现状检查）

* 结论：**仅改Prompt可以落地基础角色差异，但要稳定实现“批发/零售按数量切换”需要最小代码配套**。

* 已发现的现状限制：

  * `ShoppingRequest` 当前只有 `request/hidding/price/dislike/followUp/decided`，没有显式“购买数量/打包意愿”字段。

  * `OrchestratorService.buildContext` 仅透传上述字段与轮次信息，B商家无法稳定拿到可计算的批发触发条件。

  * 前端输入也没有数量/凑单字段，联调时只能依赖自然语言猜测，导致B商家价格策略不稳定。

* 评估后的改动建议（推荐执行）：

  * 在 `ShoppingRequest` 增加可选字段：`quantity`（默认1）、`bundleIntent`（默认false）。

  * 在 `OrchestratorService.buildContext` 透传这两个字段给子代理上下文。

  * 在 `simple_web` 增加这两个输入项，便于稳定复现“批发价/零售价”路径。

  * 同步更新测试请求样例与断言，保证回归可重复。

## 3. Prompt 重构策略（逐商家）

### 3.1 商家A（高价高服务型）

* 身份设定：

  * 非批发商，服务热情，强调品质稳定、售后保障、服务体验。

* 定价模型（商品A示例）：

  * 进货价：80

  * 挂牌价：120

  * 促销后最低：110（不可低于110）

* 输出约束：

  * `coupon_info.original_price=120`

  * `coupon_info.after_coupon_price=quote`

  * `quote` 范围：`[110,120]`，且不超用户预算

  * `coupon_desc` 需解释从120到最终价的券/活动构成

* 话术风格：

  * 强调品质、售后、服务响应，不夸大不可核验承诺。

### 3.2 商家B（批发导向型）

* 身份设定：

  * 批发商角色，主打“量大更优惠、跨品打包优惠”。

* 定价模型（商品A示例）：

  * 进货价：60

  * 挂牌价：105（批发）/115（零售）

  * 大单最低：100

* 输出约束：

  * 需根据上下文条件（数量、是否打包）给出零售或批发场景

  * `coupon_info.original_price` 只能取 `105` 或 `115`

  * `quote` 不低于100，且满足 `after_coupon_price=quote <= original_price`

  * `coupon_desc` 要明确“触发条件”（如2件以上或同店凑单）

* 话术风格：

  * 强调批发优势与条件优惠，避免空泛“神秘补贴”。

### 3.3 商家C（察言观色动态型）

* 身份设定：

  * 非批发商，具备“多轮动态调价与策略调整”能力。

* 定价模型（商品A示例）：

  * 进货价：80

  * 基础挂牌价可围绕指导价/场上竞争态势设置

  * `round=1` 给初始报价；`round>=2` 结合 `previousReplies/competitorReplies` 调整报价与卖点

* 输出约束：

  * 不可低于进货价，不可高于用户预算

  * 需要在 `reason_tags` 或 `coupon_desc` 体现“为何本轮调整”

  * 保持价格字段自洽：`quote=after_coupon_price<=original_price`

* 话术风格：

  * 兼顾真实、克制和应变，避免与前轮完全重复。

## 4. 通用价格规则重写（写入三个 Prompt）

* 明确三层价格概念：

  * 指导价（公开参考）

  * 进货价（商家内部）

  * 挂牌价与最终成交价（券后quote）

* 对进货价比例规则进行统一约束：

  * 批发商身份：进货价约为指导价40%

  * 非批发商身份：进货价约为指导价50%

* 结构化硬约束：

  * `quote`、`original_price`、`after_coupon_price` 均为正数

  * `after_coupon_price = quote`

  * `after_coupon_price <= original_price`

  * `subsidy_by`、`stackable` 必填且可解释

* 要求在 `message/cta` 中包含“挂牌价与券后价”的可读说明。

## 5. 实施步骤

1. 重写 `seller_a.txt`，注入A商家角色与价格规则、服务型话术模板、字段硬约束。
2. 重写 `seller_b.txt`，注入批发/零售双挂牌价机制与大单优惠触发条件。
3. 重写 `seller_c.txt`，注入多轮动态调价机制（读取 round 与竞品回放）。
4. 对齐三个 Prompt 的 JSON 输出示例，确保字段名与后端解析一致。
5. 增加请求侧最小字段支撑（`quantity/bundleIntent`）并透传到子代理上下文。
6. 更新前端输入与测试样例，覆盖“零售场景/批发场景/多轮动态调价场景”。
7. 运行编译与测试，确认重构未破坏既有结构化输出链路。
8. 启动三服务并执行给定模拟入参（含数量与凑单场景）联调，采集完整SSE流。
9. 按结果集规范补充“Prompt修改前后对比、修改逻辑、效果验证”，生成且仅保留一个结果文件。

## 6. 验收标准

* A/B/C 三个 Prompt 与其身份、定价模型完全匹配：

  * A：120挂牌，最低110，服务型

  * B：105/115挂牌，大单最低100，批发型

  * C：多轮动态跟随型，报价可随轮次与竞品变化

* 子代理输出保持结构化且字段完整，不触发异常兜底覆盖。

* 当 `quantity>=2` 或 `bundleIntent=true` 时，B商家可稳定落入批发或打包优惠路径；否则默认零售路径。

* SSE `subAgentReplay` 中可观察到“挂牌价与券后价”逻辑可解释。

* 给定模拟入参重测后，结果集完整保留原始SSE全量事件，不再省略。

* 结果文件仅一个，内容包含：修改场景、前后对比、验证日志、完整原始流。

## 7. 风险与规避

* 风险1：Prompt规则过严导致模型不稳定输出\
  规避：在每个Prompt保留最小可行JSON模板+错误回退指引。

* 风险2：`SubAgentController` 兜底覆盖导致价格特征不明显\
  规避：确保Prompt内价格关系严格自洽，减少兜底触发概率。

* 风险3：多轮动态调价信息利用不足\
  规避：在C商家Prompt显式要求读取 `round/previousReplies/competitorReplies` 并写入本轮策略变化。
