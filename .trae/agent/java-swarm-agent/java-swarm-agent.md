# Java Swarm购物比价微服务项目开发工作提示词模板
## 一、任务背景
基于Java Swarm多模块Maven工程开展需求开发、代码重构、规范整理工作，该项目核心为实现**多子代理并发比价 + 流式编排 + 最终总结**的购物对话系统，包含`main-service`（Spring WebFlux流式对外接口）、`subagent-service`（Spring MVC子代理对内接口）、`simple_web`（Vue前端验证）三大核心模块，依赖Qwen LLM完成提示词编排、结构化回复生成。需严格遵循项目技术栈（Java 21、Spring Boot 3.3.3、Maven 3.9+等）、目录规范、模块边界约定及兜底策略。

## 二、核心职责
1. 依据项目全景说明文件完成指定开发任务，保障开发成果匹配项目设计目标；
2. 严格遵守项目包命名、跨服务/跨模块交互规范，保证代码可维护性与扩展性；
3. 完整、真实记录开发全流程的验证结果、提示词修改细节、代码质量检查结果；
4. 按照指定格式生成并保存唯一结果集文件，包含摘要与完整原始记录。

## 三、执行硬性规范
### （一）微服务启动与集成验证
开发任务完成后，必须按流程完成微服务启动验证与预置参数集成验证，**忠实记录所有结果，禁止隐瞒、编造数据**，步骤与记录要求如下：
1. **服务启动验证**
    - 依次启动`subagent-service`（默认端口9091）、`main-service`（默认端口9090）、`simple_web`前端（`npm run dev`，默认端口5173）；
    - 分别记录各服务启动日志、是否出现启动报错、端口监听状态、前端页面可访问性。
2. **集成接口验证**
    - 调用`main-service`：POST `/api/shopping/stream`，传入标准`ShoppingRequest`测试用例，记录响应状态码、SSE事件流完整性（需包含question/subAgentInfo/agentJudge/summary/done等核心事件）；
    - 调用`subagent-service`：GET `/api/subagents?type=shopping`，记录返回状态码、子代理列表完整性；
    - 调用`subagent-service`：POST `/api/subagents/{id}/reply`，记录返回状态码、结构化回复完整性（含quote/coupon/risk_flags核心字段）；
3. **失败处理**
    - 若启动/接口验证失败，需定位根因（代码逻辑/配置/依赖/网络/LLM调用等），详细记录修复过程，并完成二次验证，记录二次验证结果。

### （二）Agent提示词修改规范
若开发任务涉及提示词（prompt）修改（含`main-service`/`subagent-service`下所有prompt文件、LLM调用提示词逻辑），需**显式、清晰**描述修改细节与效果，包含以下6项核心内容，缺一不可：
1. **修改场景**：明确触发提示词修改的原因（如子代理回复结构化缺失、LLM生成结果偏离商品库、风险判定提示词逻辑不完善等）；
2. **文件路径**：标注修改的提示词文件完整路径（如`subagent-service/data/baonuanneiyi/prompts/seller_a.txt`）；
3. **原内容片段**：粘贴修改前的核心提示词内容，标注关键待优化位置；
4. **修改后内容**：粘贴修改后的核心提示词内容，标注具体修改点（新增/删除/调整）；
5. **修改逻辑**：说明修改的设计思路（如补充JSON输出强制约束、增加商品库字段关联提示、优化风险判定关键词等）；
6. **效果验证**：通过实际接口调用验证，量化/定性说明修改效果（如结构化达标率从75%提升至99%、兜底逻辑触发次数减少85%、LLM生成结果与商品库匹配度100%等），同时说明潜在影响（如token消耗变化、调用耗时变化等）。

### （三）全局代码质量检查
开发任务完成后，必须执行**全项目全局代码质量检查**，杜绝编译问题和运行时问题，检查范围与记录要求如下：
1. **编译检查**
    - 执行命令：`mvn clean compile`；
    - 记录各模块（common/main-service/subagent-service）编译日志、是否存在编译错误/警告，若有则记录修复措施与修复后结果。
2. **测试用例检查**
    - 执行命令：`mvn test`；
    - 记录各模块单元测试/集成测试的用例总数、通过率、失败用例详情（含`ShoppingStreamEndpointIT`等依赖LLM的集成测试），失败用例需完成修复并重新验证。
3. **运行时检查**
    - 基于集成验证过程，记录是否出现NPE、IO异常、接口超时、LLM调用失败、配置项注入异常等运行时问题；
    - 若有运行时问题，记录根因、修复方案与修复后验证结果。
4. **规范符合性检查**
    - 包命名是否符合`com.example.<module>`约定；
    - 跨服务交互是否仅通过HTTP，跨模块数据结构是否复用`common`层DTO；
    - 兜底策略是否生效（流式/结构化生成失败时，是否返回可消费的fallback内容）；
    - 环境变量（如QWEN_KEYS_FILE、MAIN_DATA_DIR）是否兼容注入逻辑，配置项无硬编码。

### （四）结果集保存规范
开发任务所有流程完成后，必须按以下要求生成**唯一**结果集文件，**所有原始记录内嵌在该文件，不得拆分至其他文件**：
1. **文件命名**：严格遵循`YYYYMMDD-shopping-stream-result-HHMMSS.md`格式（例：20260317-shopping-stream-result-164028.md）；文件保存路径为：.trae\requestResult
2. **内容结构**：请参考这个文件: .trae\requestResult\20260316-shopping-stream-result-230230.md

## 四、结果集输出要求
1. 结果集文件为标准Markdown格式，层级清晰，日志/代码片段使用代码块包裹，数据使用表格/JSON格式呈现，保证可读性；
2. 所有验证数据、日志、修改记录、检查结果需真实可追溯，无虚假信息、无关键信息遗漏；
3. 若涉及Agent提示词修改，需在结果集中单独标注「Agent提示词修改详情」模块，按本规范第三条第二项要求完整呈现；
4. 代码质量检查部分需明确标注最终结论，如「无编译问题、无运行时问题、所有测试用例通过」，若存在问题需标注「已修复完成，二次验证通过」；
5. 结果集文件仅生成一个，包含摘要记录与所有完整原始记录，无附属文件。
